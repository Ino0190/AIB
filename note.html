AWS Certified AI Business Strategist (AIB-C01) 学習ノート

公式試験ガイドの4ドメイン・Task・Skillを日本語で整理。用語の正体と「どっちを選ぶかの判断軸」に寄せてある。

性格：AIを作る人でなく、評価・推進・拡大する人の試験。コード・AWS実装経験は不要。
時間・合格：130分／100〜1000スケールで700。補償方式（ドメイン別の足切りなし）。
形式：択一（正解1・誤り3）と複数選択（5択以上から2つ以上・全部当てて初めて得点）。未回答は不正解、当て勘に減点なし＝空欄を残さない。
配分：D1 基礎24% / D2 戦略28%（最大） / D3 統治24% / D4 変革24%。
前提：AI導入チームと並走6か月程度。Bedrock / SageMaker AI / Amazon Quick を「高レベルで何をする物か」だけ知っていればよい。

この試験の解き方の型 SAA・DEAとの違い

SAAのクセを持ち込むと落ちる

  • サービス名を選ぶ問題がほぼ無い。「どのAWSサービスか」でなく「どの経営判断か」を選ぶ。選択肢に技術実装（インスタンス選定・パイプライン構成）が出たら、それは範囲外＝罠。
  • 「立派な言葉」が誤答になる構造は同じ。ファインチューニング・独自モデル構築・全社一斉展開は、要件を読むと過剰になっていることが多い。
  • 「AIを使わない」が正解の問題が必ずある（Skill 2.1.4・1.2.1）。規則が明確で例外が少ない業務はルールベース自動化が正解。

正解を決める3つの読み方

  1. 最後の1行の要件語で切る：「まず最初にすべきことは」「最も可能性が高いのは」「最小の労力で」「経営層に示すには」。同じ状況でも聞き方で答えが変わる。
  2. 順番を問う問題は「測る前・測った後」で切る：基準線（ベースライン）取得 → 導入 → 効果測定。「先に何をするか」なら基準線・データ準備・責任の明確化が先。
  3. ガバナンスは「後付けでなく設計時」が常に正しい（governance by design）。「本番後に監視を入れる」系は誤答。
複数選択の潰し方

2つ選ぶ問題は「軸が違う2つ」が正解になりやすい。同じ軸の似た選択肢が2つ並んでいたら、片方はニアミスの誤答。人・プロセス・技術・ガバナンスの4軸を思い出して、別軸から1つずつ取る。

データ品質が効く理由（Skill 1.1.4 の答え方）

  • モデルはデータに含まれる偏りをそのまま学ぶ。過去の不公平な判断を学習すれば、不公平をさらに速く大量に再生産する。
  • 品質が悪いままアルゴリズムを高度にしても改善しない。「まず何をするか」型の問題ではデータ品質・データ準備が正解になりやすい。
国際規格 ISO/IEC 23053 と 42001（Skill 1.1.6）
規格何の規格か覚える一言
ISO/IEC 23053MLを使うAIシステムを記述する共通の枠組み・用語言葉を揃えるための規格
ISO/IEC 42001AIマネジメントシステム（AIMS）の規格。認証を取れる組織として統治するための規格

「全社でAIの用語・分類がバラバラ」→23053系の語彙統一。「AIガバナンスを第三者に示したい・認証が欲しい」→42001。

Task 1.2 どのソリューション型を選ぶか

AIを使わない判断（Skill 1.2.1）— この試験の頻出

状況正解理由
規則が明文化され例外が少ない（税率計算・与信の閾値判定・承認フロー）ルールベース自動化結果が説明可能・安価・監査しやすい。AIは過剰
規則が厳密に守られなければならない（法令の必須項目チェック）ルールベース確率的な出力は許されない
入力のパターンが無数（自由記述の問い合わせ分類・画像判定）AI/MLルールを書き切れない
学習データが無い・少ない、または問題の定義が曖昧AIを採用しない（Skill 2.1.4）作っても価値が出ない

AIエージェント（Skill 1.2.2）

単発で答えを返すだけのAIと違い、目標を与えると自分で段取りして動くもの。試験で問われる中核能力は4つ。

  • 自律性（autonomy）：次に何をするかを自分で決める
  • ツール利用（tool use）：検索・社内API・DB照会などを自分で呼ぶ
  • エージェント間通信（agent-to-agent）：複数のエージェントが役割分担して連携する
  • オーケストレーション戦略：どの順で誰に任せるかを統括する仕組み

経営視点の含意＝自律的に動くほど人の監督点（human oversight）と権限の範囲を先に決める必要が増す。D3と必ず結びつけて出る。

継続監視とドリフト（Skill 1.2.3）

用語中身対処
モデルドリフト現実が変わってモデルの前提がずれ、精度が静かに落ちる継続監視・再学習の運用を最初から計画
データ品質劣化入力側の仕様変更・欠損増加で出力が崩れる入力の監視も対象に含める
バイアスドリフト運用中に偏りが増大する（Skill 3.3.2）公平性の指標を定期測定

「導入したら終わり」は必ず誤答。AIは導入コストでなく運用コストの物、と覚える。

シャドーAI（Skill 1.2.4）

従業員が会社の承認なく外部AIツールを使う状態。機密漏洩・IP・コンプライアンスのリスク源。

正解の型＝禁止でなく「透明な分類」：承認済み / 禁止 / 評価中 の3分類を公開し、承認済みの使える道を用意する。全面禁止は水面下利用を増やすので誤答になりやすい。

Task 1.3 生成AIの技法

プロンプトエンジニアリングの原則（Skill 1.3.1）
  • 役割・文脈・制約・出力形式を明示する（曖昧な指示は曖昧な出力）
  • 例を見せる（少数例＝few-shot）と精度が上がる
  • 長い課題は手順に分解して段階的に指示する
  • プロンプトで直せるのは「指示の与え方」の問題だけ。知識が足りない問題はプロンプトでは直らない（→RAG）

トークンとコンテキストウィンドウ（Skill 1.3.2）

用語中身効いてくる所
トークンモデルが扱う文字のかたまり。入力＋出力の量で課金されるコストの単位（消費ベース課金）
コンテキストウィンドウ一度に渡せる上限。超えると古い部分が落ちる長文契約書の一括処理・長い会話の記憶で破れる

症状の読み方：長い会話で前の指示を忘れる／長文の後半だけ要約が雑になる → コンテキスト上限の問題。費用が想定を超える → トークン量の問題。

モデル適応の3段階（Skill 1.3.3）— 選択の判断軸

手法何をする選ぶ条件コスト
プロンプトエンジニアリング指示の書き方を工夫するまず最初に試す。汎用知識で足りるほぼ0
RAG社内文書を検索して根拠として渡す社内の最新情報・出典が必要・情報が頻繁に変わる低〜中
ファインチューニングモデル自体を追加学習する専門用語の語調・独自の出力形式を体に入れたい。教師データが大量にある高（再学習の度に発生）
決め手：「社内規程を根拠付きで答えたい」「情報が毎月変わる」「出典を示したい」→RAG。ここでファインチューニングを選ぶのが典型的な誤答（＝立派な言葉の罠）。逆に「回答の言い回し・形式を自社流に固定したい」はファインチューニング。

Build / Buy / Partner（Skill 2.1.2）

選択選ぶ条件代償
Buy（既製・SaaS・Marketplace）短納期・一般的な業務・社内にAI人材がいない・まず試したい差別化にならない・カスタマイズに限界
Build（自社構築）それ自体が競争優位の源泉・独自データがある・長期に持つ覚悟と人材がある費用・期間・運用責任が最大

判断に入れる要素は予算・期間・自社の能力・ベンダー提案・規制対応の5つ。「一番安いから」「一番高機能だから」の単独理由は誤答。

優先順位づけと止める判断（Skill 2.1.3）

軸は事業価値 × 実現可能性 × 持続可能性 × 戦略適合。結論は3つしかない。

  • Scale（拡大）：価値が出て再現性がある
  • Pause（一時停止）：前提条件（データ・規制・体制）が未成熟。条件が整えば再開
  • Terminate（中止）：価値が出ない／前提が崩れた。撤退も正解の選択肢（サンクコストで続けるのは誤答）

AIが適切でない場合（Skill 2.1.4）

  • 規則が明確で例外が少ない → ルールベース
  • データが無い・偏っている・品質が担保できない
  • 誤りの影響が致命的で、確率的な出力を許容できない
  • 問題の定義や成功の測り方が決まっていない
  • 単純な業務改善・プロセス設計で解決する（そもそもの業務が無駄）

移行時の検討事項（Skill 2.1.5）

既存業務をAIに移すとき／AIプラットフォームを乗り換えるときに見る4点。

観点具体
事業継続性切替中に業務が止まらないか。並行稼働・段階移行・切り戻し手順
コストへの影響移行費用に加え、推論単価・課金モデルの違い、二重稼働期間の費用
データ準備性移行先で使える形か。データの持ち出し可否・ロックイン
性能への影響精度・応答速度が現行より落ちないか。同じプロンプトが別モデルで同じ結果にならない

Task 2.2 価値の測定 — 配点の中心

Skill 2.2.2 ベースライン（基準線）— 最重要の1問

AI導入の「前」に現状値を測っておく。これが無いと後から効果を主張できない。「導入したが効果を示せない」という状況の原因は、ほぼ必ず基準線の欠如。

「導入前にまず何をすべきか」型の問題ではベースライン測定が正解。

KPIの2分類（Skill 2.2.1）

種類例扱い
有形（tangible）コスト削減額・売上増・処理時間短縮・人件費金額に換算できる。ROIの分子
無形（intangible）顧客満足度・従業員の生産性実感・従業員定着・ブランド金額化しにくいが測らないのは誤り。代理指標（NPS・離職率・アンケート）で測る

「無形の効果は測れないので対象外」は誤答。有形だけで判断するとAIの価値を過小評価する。

ROIの枠組み（Skill 2.2.3）

ROI ＝（便益 − コスト）÷ コスト。便益に入れる4系統＝時間削減・コスト削減・売上増・生産性向上。

コスト側に入れ忘れやすいもの
  • 推論（トークン）の継続費用 ← 最大の見落とし
  • データ整備・ラベリングの工数
  • 統合・既存システム改修
  • 研修・チェンジマネジメント
  • 監視・再学習・ガバナンスの運用費

先行指標（Skill 2.2.4）

成果（遅行指標）が出る前に成功を予測できる指標。「まだROIが出ていないが順調か知りたい」型の答え。

  • 利用率・アクティブユーザー数（作ったが使われていない兆候を早く掴む）
  • AIの出力が人にどれだけ修正されたか（修正率が下がる＝役に立ってきている）
  • 研修受講率・AIリテラシーの広がり
  • 経営スポンサーの関与度・ユースケース申請数

コスト管理（Skill 2.2.5）

課金モデル中身合う使い方
消費ベース（従量・トークン）使った分だけ。Bedrockのオンデマンド等利用量が読めない初期・PoC
インスタンスベース確保した計算資源に対して時間課金安定して大量に使う・専用スループットが要る
シートベース利用者1人あたり月額業務アシスタント系（Amazon Quick等）

最適化の打ち手＝用途に合う小さいモデルを選ぶ／不要な長文プロンプトを削る（トークン削減）／キャッシュ・バッチ処理／安定利用分はSavings Plans等のコミット割引／AWS Pricing Calculatorで事前見積・Cost Explorerで実績分析。

Task 2.3 競争優位としての位置づけ

  • Skill 2.3.1：競合の成熟度を見て、追随か先行かを決める。「競合がやっているから」だけでは投資判断にならない。
  • Skill 2.3.2：ビジネスモデル自体の転換機会（売り切り→従量サービス化、製品→データを使った予測サービス）。既存業務の効率化より大きい効果。
  • Skill 2.3.3：持続する優位はモデルではなく、独自データ・業務への組み込み・組織の能力から生まれる。基盤モデルは誰でも買えるので、それ自体は優位にならない。
  • Skill 2.3.4：投資水準は業界の成熟度と競争の激しさで決める。全業界一律に「最大投資」は誤答。規制が厳しく成熟が遅い業界では慎重な段階投資が正解になりうる。

Task 3.1 責任あるAIの原則

次元中身問題文に出る症状
公平性 fairness特定の属性に不利な結果を出さない採用・与信で特定層の通過率が低い
説明可能性 explainabilityなぜその出力になったか説明できる「顧客に理由を説明する義務がある」「規制当局に示す」

Skill 3.1.2 トレードオフの捌き方 — 判断問題の核心

事業目標と責任あるAIが衝突したとき、試験の正解は「片方を捨てる」ではない。

衝突正解の方向
精度を上げたいが説明できないモデルになる用途で分ける。規制・人生に影響する判断は説明可能な方式＋人の確認を入れる
早く出したいがバイアス検証が終わらない範囲を限定して出す（限定公開・人の監督付き）。検証を飛ばして全面公開は誤答
個人データを使えば精度が上がる目的・同意・最小限の範囲に絞る。「精度のため全部使う」は誤答
コスト削減のため人の確認を外したい影響度でリスク分類し、高リスクだけ人を残す

共通の型＝リスクの高さで扱いを分ける。全部同じ厳しさにするのも、全部緩めるのも誤答。

Skill 3.1.3 ガバナンス・バイ・デザイン

責任あるAIの検討は企画・計画の段階から入れる。「本番稼働後に問題が出たら対処する」「まずPoCを作ってから考える」は誤答。後から入れると手戻りが大きく、すでに損害が出ている。

Skill 3.1.4 人の監督と安全装置

安全装置役割
ガードレール入力・出力を制限して不適切な内容や機密を弾く（Amazon Bedrock Guardrails）
ハルシネーション検出根拠のない出力を見つける。出典提示・RAGの根拠突合
エスカレーション基準確信度が低い・高額・苦情・例外のときに人に回す条件を先に決める
人による確認（human in the loop）最終決定を人が持つ。採用・与信・医療・法務など人に重大な影響が及ぶ判断では必須

Task 3.2 統治構造と規制対応

Skill 3.2.1 AIガバナンス体制

  • 部門横断で作る：事業部門・技術・法務・コンプライアンス・セキュリティ・リスク管理・人事。「IT部門だけで運営する」は誤答。
  • 説明責任を明確にする：ユースケースごとに承認者・オーナー・監視責任者を決める。「AIが決めたことだから誰も責任を負わない」は成立しない。
  • 審査・承認のプロセス、記録、定期レビューを持つ。

Skill 3.2.2 規制対応

業界・地域で要求が違う（医療・金融・個人データの越境移転・自動意思決定の説明義務など）。ポイントは「どの法律か」を暗記するのではなく、規制要件を早期に特定して設計に織り込むこと。ベンダー選定（Skill 2.1.2）でも規制適合は必須条件。

Skill 3.2.3 アクセス制御とデータ保護

  • 最小権限。AIが参照できる範囲を役割で絞る。
  • 人の閲覧権限とAIに渡す範囲は別に決める。権限があってもAIに入れない区分（診断情報・相談記録など）を持つ。
  • 保存時・通信時の暗号化、監査ログ、データ保持と廃棄の方針。
  • AWS責任共有モデル：AWSはクラウド「の」セキュリティ（基盤・物理・サービス自体）、利用者はクラウド「内の」セキュリティ（自社データ・アクセス権・使い方・プロンプトに何を入れるか）。マネージドサービスを使ってもデータの責任は利用者側に残る。

Skill 3.2.4 AIリスク分類

全ユースケースを同じ厳しさで審査すると回らない。影響度でクラス分けして、統治の強さを変える。

リスク水準例統治の強さ
低社内文書の要約・議事録の下書き簡易チェック・利用ガイドラインのみ
中顧客向けチャット・マーケ文面生成ガードレール・出力レビュー・監視
高与信・採用・医療・安全に関わる判断人の最終決定必須・バイアス検証・説明可能性・監査記録・上位承認

Task 3.3 企業のAIリスクと緩和

Skill 3.3.1：本番のAIには「リスク管理の仕掛けと監視」が必要。作った時点のテストで終わりにしない。ここもD1のドリフトと同じ結論に着地する。

D4 ビジネスレディネス・リーダーシップ・AI変革 24%

Task 4.1 成熟度評価 / 4.2 データと基盤 / 4.3 変革と人材 / 4.4 拡大

Task 4.1 準備度と成熟度

Skill 4.1.1 評価する5つの次元

次元見るもの欠けたときの症状
経営の同意（leadership alignment）スポンサーがいて優先順位が合っているか予算と人が付かず立ち消える
データ品質使える状態か・どこにあるかPoCで止まる最大の原因
文化の準備変化と失敗を許容できるか現場が使わない
技術基盤計算資源・統合・セキュリティ拡大時に破れる
ガバナンス枠組み承認・責任・監視の仕組み本番に出せない

Skill 4.1.2 AI成熟度モデル

段階は「実験 → 部門で運用 → 全社展開 → AIが事業に組み込まれた状態」。試験の型＝現在地に合った打ち手を選ぶ。実験段階の組織に「全社CoEと大規模投資」を当てるのも、全社展開段階に「まずPoCを1つ」と言うのも誤答。

Skill 4.1.3 能力ギャップの4軸

人（People）・プロセス（Process）・技術（Technology）・ガバナンス（Governance）。この4軸は複数選択問題で「軸違いの2つを選ぶ」ときの道具になる。技術だけ手当てして人とプロセスを放置するのが典型的な失敗。

Task 4.2 データと基盤

  • Skill 4.2.1 データ準備性：品質・アクセス可能性・サイロ。部門ごとにデータが分断されていると、部門横断のユースケースが作れない。「AIの前にデータ統合」が正解になる場面。
  • Skill 4.2.2 データ戦略：データオーナーシップ（誰がその データの正本を持ち品質に責任を負うか）とデータ共有の枠組み（部門間でどう渡すか・誰が承認するか）。技術で解く前に決める統治の話。
  • Skill 4.2.3 技術基盤：計算資源・ストレージ・統合（既存システムとつながるか）・セキュリティ。拡大の段階で足りなくなるので、PoCの時点で全社展開時の要件を見ておく。

Task 4.3 全社変革と人材

Skill 4.3.1〜4.3.2 体制

  • 経営スポンサーシップ：役員レベルの後ろ盾。これが無いAI施策は途中で失速する（最頻出の失敗原因）。
  • AIチャンピオン：各部門で推進する人を見つけ、権限と時間を与える。上からの号令だけでは現場が動かない。
  • 部門横断チーム：事業リード・技術専門家・法務・コンプライアンスを揃え、明確な責任分担を置く。

Skill 4.3.3 従業員への伝え方

不安の中身は「自分の仕事が無くなるのでは」。正解の型は透明な情報開示：導入時期、期待する成果、役割にどう影響するかを早く正直に伝える。「不安を招くので詳細は伏せる」「決まってから知らせる」は誤答。噂が先に広がる。

Skill 4.3.4 文化の壁と介入

壁リーダーの介入
リスク回避的小さく安全に試せる場を用意する（限定範囲のPoC）
変化への抵抗現場が痛い業務から始めて、効果を当事者の言葉で共有する
失敗への恐れ実験の失敗を責めない方針を経営が明言する・学びを評価する
不信（精度・仕事の喪失）人が最終決定を持つ設計を示す・研修で触らせる

Skill 4.3.5 AIリテラシーを広げる手段

  • PoCプログラム（現場が自分の業務で試す）
  • ハッカソン（短期間で体験させる・チャンピオン発掘に効く）
  • 役割別の研修プログラム（経営層・管理職・現場で内容を変える）
  • 責任あるAIの研修（使い方だけでなくリスクと禁止事項）

Skill 4.3.6 人の役割の移し方

「作業する人」から「AIを監督し協働する人」へ。人の強み＝批判的思考・共感・創造性・例外判断・責任を負うこと。AIの強み＝速度・量・一貫性・24時間。置き換えでなく分担を設計するのが正解の方向。

Task 4.4 パイロットから全社展開へ

Skill 4.4.1 反復的な変革の4フェーズ

Envision（構想）→ Experiment（実験）→ Launch（立ち上げ）→ Scale（拡大）

AWS CAFの考え方と同じ並び。一足飛びに全社展開は誤答。逆に、実験を繰り返すだけで本番に出さない「PoC地獄」も誤答。

  • Skill 4.4.2：短期の成果（quick win）から始め、それを足場に全社へ広げる。最初に全社基盤を完璧に作ってから始めるのは遅すぎる。
  • Skill 4.4.3 CoE（センターオブエクセレンス）：知見・標準・再利用部品・ガバナンスを集約する横断組織。複数部門で同じ試行錯誤が重複し始めたときが設置のタイミング。1件目のPoCの前に作るものではない。
  • Skill 4.4.4：継続的なフィードバックの仕組みと成功指標を置き、短期の効果だけでなく長期の価値を追う。
  • Skill 4.4.5 実験から本番へ：PoCと本番の差はガバナンスと運用要件。監視・SLA・サポート体制・障害時の手順・再学習・監査記録・責任者。「PoCで動いたからそのまま本番」は誤答。
  • Skill 4.4.6：拡大の過程で事業継続性と性能を確保する。利用者が増えたときのコスト・レイテンシー・品質の劣化を事前に見る。
